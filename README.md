# Kimi 参与实时决策的 v4 智能体

从已验证的 `fiber_v2` 派生。目标是让模型参与实际运行，效果需要与纯算法版对照测试，
不能把 `fiber_v2` 的成绩当成 Kimi 版成绩。

## 模型参与的位置

1. **天气理解**：在巡天开始、约三分之一、约三分之二的夜晚，读取当前简报和适用预报，
   给出应回避的方向及 1.00—1.15 倍曝光裕量。方向影响候选排序，裕量直接调整曝光完成度估计。
   建议两小时后过期，之后恢复算法默认值。
2. **行动决策**：上述时点的下一次可行观测，把最多四个候选方案交给模型选择。
   候选包含曝光、观测程序、必选目标预计完成数和限时请求；只接受给定编号。
   被选方案决定实际指向、光纤目标、曝光与观测程序。
3. **故障研判（按需）**：跨夜证据达到阈值后，模型可确认或否决故障报告。

天气理解和行动选择若因临时网络问题失败，会分别安排在下一观测夜补试；已成功的环节
不重复补试。补试使用下一夜的新公告、候选和剩余时间，不采用上一夜迟到的回复。

故障诊断按每次曝光汇总光纤样本，比较连续两夜与更早的记录，避免同一次曝光的多根光纤
挤掉跨夜证据。两夜都要下降、证据必须在两小时内更新，并经多次间隔确认；启动怀疑需要
更大的跌幅，确认恢复则需要回升到较高水平。模型也会收到仍可免罚的误报次数下界。

候选预计收益率不能低于算法最佳值的 85%；这只是预测范围约束，不是实际得分保证。
模型不执行代码，也不计算目标能否落进光纤。程序负责几何、曝光和协议验证。
调用失败、输出格式错误、没有密钥时使用确定性选择。天气建议仍有短期记忆，故障研判
仍有跨夜证据和报告冷却时间。

默认每卡最多 8 次请求、每次最多等待 20 秒、累计等待最多 120 秒；剩余真实时间不足
90 秒时停止调用。临时超时只使相应环节当夜回退，下一夜可以继续；每个环节每夜最多
尝试一次。旧请求线程尚未退出时不启动新请求，迟到的模型建议被丢弃。
HTTP 400/401/403 属于参数或认证错误，仍会停止本轮后续请求，包括迟到的此类错误。
跨夜不会重置调用次数或等待预算。
900 秒还包括搜索和通信，因此这些上限不保证任何机器都能完成全场。

## 配置

独立仓库的本地配置放在根目录 `.env`；新环境可复制 `.env.example` 后填写。
在完整开发工作区中，该目录对应 `agents/fiber_kimi/`。
已有配置不要覆盖。当前版本需要同时设置接口地址、模型和密钥：

```dotenv
OPENAI_BASE_URL=https://api.kimi.com/coding/v1
OPENAI_MODEL=kimi-for-coding
OPENAI_API_KEY=在这里填写自己的密钥
AGENT_LLM_REASONING_EFFORT=low
```

组委会当前规则明确给出上面的 Coding Plan 接口及 `kimi-for-coding` / `k3` 模型选项。
Kimi 通用指南同时限制非交互式自动化，赛事适用范围应以组委会与服务方的专门安排为准；
本项目不伪装客户端身份。更换服务商时，接口、模型、密钥需要配套更换。

## 仓库提交与独立打包

本目录就是一个独立参赛项目：`observer.project.json` 位于仓库根目录，平台从
`agent.py` 启动。不需要为四张任务卡分别创建仓库，任务卡内容由平台在运行时发送。
仓库地址：<https://github.com/Veirsune/hackathon-survey26>。

独立仓库可以运行不联网的客户端回归测试，覆盖超时、次夜恢复、请求并发与预算：

```powershell
python -m unittest discover -s tests -v
```

提交时选择 GitHub 仓库，或在本仓库目录中生成 ZIP：

```powershell
python pack_agent.py --out ../submissions/fiber-kimi-agent.zip
```

平台运行需要在「参赛」页配置模型服务。`.env` 被 Git 和打包脚本同时排除，
只提交空密钥模板 `.env.example`。本仓库包含智能体、客户端回归测试及打包工具；本地裁判、测试数据、
历史结果保留在开发工作区中，不随参赛仓库上传。

以下调试命令用于完整开发工作区，独立参赛仓库不包含这些 `tools/` 文件。
在开发工作区根目录运行：

```powershell
# 只检查配置，不发请求，不显示密钥
python tools/v4_check_model.py
# 发一次连接测试，会使用少量 API 额度
python tools/v4_check_model.py --live
# 先跑一张本地卡；不要同时启动四张，以免竞争模型额度和计算资源
python tools/v4_run_local.py --card L1 --agent "python -u agent.py" --agent-cwd agents/fiber_kimi --out outputs/v4/kimi-new-run/L1
# 打包只包含代码及配置模板，自动排除 .env
python tools/v4_pack_agent.py --agent agents/fiber_kimi --out submissions/v4/fiber-kimi-agent.zip
```

本地运行器读取智能体目录中的 `.env`。直接启动 `agent.py` 不会自行读取该文件。
平台运行从环境读取 `OPENAI_BASE_URL` / `OPENAI_API_KEY`；manifest 设置默认模型。
在「参赛」页填写接口、模型和 Key，上传完整项目 ZIP。隐藏决赛要按官网要求选择
密钥“加密保存”；只保留在页面的密钥无法用于无人值守的隐藏评测。

## 记录与验证

`agent.log` 中的 `model_advice` 记录每个环节的接受状态、应用参数和候选选择；
`model_summary` 统计网络请求、成功回复、各环节接受次数以及改变默认选择的次数。
调用成功但选择算法最佳方案也是一次有效决策；不应为了做出差异而强行选次优方案。
失败回退不会伪装成成功模型调用。

可在 `.env` 设置 `AGENT_TRACE_PATH` 写额外 JSONL，路径放在智能体目录之外，避免打入 ZIP。
不能仅凭“发了两次请求”承诺满足评奖要求，最终由组委会核验代码与运行证据。

## 与官方 Python 示例的对照

2026-10-03 核查了[官方中文 README](https://github.com/gosimfoundation/hackathon-survey26/blob/main/examples/python/README.zh.md)
及配套源码。必须保持一致的是评测协议、动作字段、启动清单和平台注入的配置接口；
内部提示词、模型输出结构和调用频率可以自行设计。

| 项目 | 官方示例 | 当前 Kimi 版 |
|---|---|---|
| 评测协议 | `participant-agent-protocol-v4`；每行一个 JSON | 一致；动作字段在回复顶层，保留决策序号 |
| 输入／输出 | 接收 initialize、decision_request、finish；回复 decision_response | 一致；日志仅写 stderr |
| 项目清单 | `observer-project-v1`、`jsonl-v4`、Python 3.12 | 一致；清单位于 ZIP 根目录 |
| 模型接口 | Bearer 认证的 `/chat/completions` | 一致；优先采用平台注入的 `OPENAI_*` |
| 天气理解 | 每夜分析预报，再分析公告与累计命中率 | 三个季节节点分析天气，有效期两小时 |
| 行动选择 | 算法选择目标和指向，模型调整回避方向、曝光系数 | 模型还从最多四个合法候选中选择实际动作 |
| 故障研判 | 算法检测后请模型确认，每卡最多两次 | 同类分工，增加跨夜证据与恢复确认 |
| 调用预算 | 默认 100 次、300 秒、单次 12 秒 | 最多 8 次、120 秒、单次 20 秒 |
| 调用失败 | 一个问题最多尝试 3 次；下夜仍可调用 | 当夜回退；失败环节下夜补试，旧请求结束后才能新建请求 |

官方两个每夜调用都返回 `avoid_directions` 和 `duration_scale`，分别合并方向、平均系数。
它们属于示例内部接口，不是裁判规定的字段；本版的 `exposure_margin` 和 `candidate_id`
由程序解释后转换成标准动作，无需改成相同名称。官方也没有让模型在每次决策中自由执行代码。

官方客户端只填 Key 就能使用默认地址及 `k3`；本版客户端要求显式配置三项，提交清单提供
`kimi-for-coding` 默认模型。平台提供地址及凭证时可以正常接入，不能把本地地址写死并覆盖
平台代理。以上两种模型名均出现在组委会规则中，本次实测使用 `kimi-for-coding`。

修订 v4 已借鉴官方的跨夜恢复：临时超时不再关闭整张卡的模型调用；下一夜独立补试
失败的天气理解或行动选择环节，仍维持原调用总预算。旧请求未结束时，继续用算法观测，
直到后续夜晚可以补试。每日调用与事件触发调用仍值得做独立对照。

## 真实 Kimi 测试（2026-10-03，修订 v3）

真实接口连通测试成功。以下为同一份 v3 源码在官方本地开发卡上的单次完整测试，
不是云端 α—δ 成绩。对照为冻结的纯算法 `fiber_v2`。

| 本地卡 | 纯算法 v2 | Kimi v3 | 差异 | 总用时 | 模型请求／有效回复 | 必选遗漏 |
|---|---:|---:|---:|---:|---:|---:|
| L1 | 5619.94 | 5695.71 | +1.35% | 291 秒 | 7／7 | 2 |
| L2 | 5998.55 | 5929.00 | −1.16% | 312 秒 | 7／7 | 3 |
| L3 | 5311.28 | 5330.06 | +0.35% | 282 秒 | 3／2 | 1 |
| L4 | 4425.80 | 4385.26 | −0.92% | 278 秒 | 6／6 | 5 |
| 平均 | 5338.89 | 5335.01 | −0.073% | — | — | — |

四卡必选遗漏均与对照相同，均有天气理解和行动选择的有效模型回复；L1、L2 还各有一次
有效故障确认。共 23 次网络请求、22 次有效回复，模型等待合计约 160 秒（四卡合计）。
L3 一次请求超过 20 秒，后续调用停止，算法继续完成观测；末尾主动结束时仅余 47 秒，
小于最短 60 秒曝光，已经核对无后续可观测夜晚。

本轮有效的候选选择都选中了算法首选，模型天气建议曾改变回避方向和曝光裕量。
不能把“有效参与决策”解释成“已经提高得分”：四卡均值略低于纯算法版，且本版同时修复了
故障诊断，真实时间消耗也会改变搜索规模。这不是隔离模型贡献的消融实验。后续需要固定
搜索预算、重复运行及对照模型建议，才能评价模型的独立增益。

初版在 L2 仅得 4250.29 分，按曝光聚合后的中间版为 4103.68 分。诊断发现跨夜证据窗口
及恢复阈值导致未能及时报告仪器故障；加入双夜证据和恢复滞回后得到上表的 5929.00 分。
失败版本、运行日志和配置摘要均保留，未用后来的结果覆盖。
